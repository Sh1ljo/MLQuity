MLQuity: Step-by-Step Guide

Building López de Prado's Advances in Financial Machine Learning (AFML) yourself, in Python, on US equities with daily bars. You write the code. This guide tells you what to build, why, where the book explains it, and how to know you got it right.

How to use this guide

Every phase is built from the same parts. Work top to bottom and do not skip the checks.

1. ReadA reading plan: which book sections to read, skim, or skip, in order.
2. UnderstandThe idea in plain English, so the book reads easier.
3. BuildNumbered steps. Each says what to build, the approach, and a hint ladder for when you are stuck.
4. CheckConcrete tests with numbers you can verify by hand.
5. ExplainQuestions to answer in your own words. If you cannot, re-read that section.

The loop for every step

  1. Read the Book box. If the idea is already clear, skip the reading. If not, read exactly the sections named there.
  2. Try the step yourself before opening the hints. Struggling for 15 minutes teaches more than reading a solution.
  3. Open Stuck? Hint ladder one rung at a time. Stop at the first rung that unblocks you.
  4. Run the Check. A step is done only when the check passes, not when the code runs.

Rules for every phase

  • Write modules under src/ and tests under tests/. Notebooks are for poking at results, not for code you keep.
  • Never edit anything in data/raw/. Write derived data to data/processed/.
  • Every configuration you try (a threshold, a window, a model setting) gets a row in trials.csv, including the ones you throw away. Phase 7 depends on it.
  • Write the test first, or at least before moving on. A phase is not finished until its checkpoint passes.
  • Test on fake random data before real data (set up in Step 0). On random data your pipeline must find nothing. If it finds an edge, you have a bug.

  • No step turned bets into a daily return series. Without it you cannot compute a Sharpe ratio or run any Phase 7 statistic. This is now Phase 6, steps 6.4 and 6.5.
  • CUSUM is not in the labeling chapter. It sits in Ch 2 (§2.5.2.1). The old plan said to read Ch 3 only.
  • Sharpe units were inconsistent. trials.csv held annualised values but DSR needs per-period ones. It now stores both.
  • Fractional differencing at the book's default threshold eats most of a daily history. See Phase 3, step 3.2, for the numbers.
  • Sample weights now follow the book's return-attribution formula, not a simplified product.
  • Meta-labeling sign flip. The book's bet-size formula can flip the side when the probability is below 0.5. Phase 6 explains why you should not do that for meta-labeling.
  • Several tests were incomplete or used fixtures that did not exist. The leakage test is now specified properly, with a "break it on purpose" check.
  • PBO does not behave the way the old text implied. Details in Phase 7, step 7.8.

Limits to accept before you start

  • One stock on daily bars has very little data. A 10-year history gives a few hundred usable events. Statistical power is low. On fake random data I measured a spread of about ±0.4 in the Sharpe ratio from luck alone. Treat this project as a way to learn the method, not to find a tradable edge.
  • If you ever see a Sharpe above about 1.5 on one stock, assume a bug first. Real edges at this scale are small.
  • The honest way to get power is to pool many stocks. That is a separate extension. Build the single-asset pipeline correctly first.

    # tests/fake_data.py
import numpy as np
import pandas as pd


def make_prices(n: int = 2500, seed: int = 0, drift: float = 0.0) -> pd.DataFrame:
    rng = np.random.default_rng(seed)
    vol = np.empty(n)
    vol[0] = 0.01
    for i in range(1, n):
        vol[i] = 0.9 * vol[i - 1] + 0.1 * 0.008 + 0.0003 * abs(rng.standard_normal())
    log_ret = drift + vol * rng.standard_normal(n)
    close = 100 * np.exp(np.cumsum(log_ret))
    volume = rng.lognormal(mean=13, sigma=0.3, size=n)
    idx = pd.bdate_range("2012-01-02", periods=n, name="date")
    return pd.DataFrame({"close": close, "volume": volume}, index=idx)

    A trap I hit while testing

    When I added "noise" columns to the fake data using the same random seed as the price generator, the noise column turned out to be tomorrow's return, and the pipeline reported a Sharpe above 1.5 on random data. Always seed noise columns with a different seed from the price generator. It is also a free demonstration that the feature-importance tools in Phase 5 do catch a leak.

Python primer for this project

You do not need to be an expert. These patterns appear in almost every step. Skim now, come back when one bites you.

The patterns you will use constantly

  • A Series is one column with a label (the index) on each row. Prices by date are a Series with dates as the index.
  • .loc vs .iloc: .loc selects by label (a date), .iloc selects by position. Mixing them up is the most common silent bug.
  • Date slices are inclusive at both ends. s.loc["2024-01-02":"2024-01-04"] includes both days. This is the opposite of ordinary Python slicing and it matters in Phase 2 and 4.
  • .shift(1) moves values down one row, so today's row sees yesterday's value. It is the main defence against look-ahead bias.
  • .pct_change() gives the simple return. np.log(price).diff() gives the log return. The first row of either is NaN, and that is correct.
  • Vectorisation: a * 2 or a + b works on every row at once. Use a plain for loop only when each step depends on the previous one (like the CUSUM filter) or when you loop over events.
  • Alignment: arithmetic between two Series matches rows by index label, not position. Use .reindex(other.index) to force two objects onto the same rows. After you reindex, always check for NaN.
  • Boolean masks: s[s > 0] keeps rows where the condition is true. Combine conditions with & and |, each in parentheses.
  • NumPy datetimes: index.values gives a plain array of times you can compare with <= and >=. Useful inside loops and in np.searchsorted.
  • Generators: a function with yield hands back one result at a time. Wrap in list(...) if you need to loop over it twice.

Three habits that save hours

  • Print shapes and index ranges after every join, reindex or dropna: print(x.shape, x.index.min(), x.index.max(), x.isna().sum().sum()).
  • Assert alignment before modelling: assert X.index.equals(y.index). Cheap insurance.
  • The truncation test for look-ahead: compute something on the full data, compute it again on data cut off at date T, and assert the two agree on every date up to T. If they differ, the calculation peeked at the future. You will use this for volatility, features and signals.

The idea

Before any machine learning you need two things: clean data, and a simple strategy to beat. If a complex model cannot beat buy-and-hold, it is just noise. The baseline is also your test harness: you prove the backtest machinery works on something you already understand.

Bars are the unit of time you trade on. Daily bars: one row per trading day with close and volume.

  1. Decide your data source, deliberately

    Book

    Ch 2, §2.2 for the data types. The book does not discuss free data sources, so this step is on you.

    Why

    Your data decides what your backtest can never tell you. Two silent killers:

    • Adjusted prices. You need closes adjusted for splits (and ideally dividends). Without adjustment a 2-for-1 split looks like a 50 percent crash.
    • Survivorship bias. Free sources usually only list companies that exist today. A backtest on survivors looks better than reality because the losers that went bankrupt are missing.
    Build

    A CSV in data/raw/ with columns date, close, volume, one file per ticker, with adjusted close. For learning, one liquid stock or an index ETF is fine. Write one line in your notes about whether the source includes delisted names.

    Check
    • You can state in one sentence whether your close is split-adjusted and dividend-adjusted.
    • You know whether delisted tickers are missing. If they are, write that down as a known limitation of every result you produce.

    Until your real data is ready, develop against make_prices() from Step 0.

  2. Write the loader with strict checks

    Why

    The loader should refuse bad data loudly. A silent fix hides problems that later show up as strange results.

    Build

    load_prices(path) -> DataFrame in src/data.py. It reads the CSV, parses dates, sets the date as index, sorts, and raises ValueError if:

    • any date is duplicated;
    • any close is missing;
    • any close is zero or negative;
    • any one-day move exceeds 40 percent (almost always an unadjusted split or a bad tick, not a real move).
    Stuck? Hint ladder
    1. pd.read_csv(path, parse_dates=["date"]), then .set_index("date").sort_index().
    2. Duplicates: df.index.duplicated().any(). Missing: df["close"].isna().any().
    3. Biggest move: df["close"].pct_change().abs().max().
    Check
    • Write four tiny CSVs in a temporary folder (use pytest's tmp_path): one duplicate date, one missing close, one negative close, one 60 percent jump. Each must raise ValueError.
    • A clean CSV loads, is sorted, and has a unique index.

  3. Buy-and-hold baseline

    Book

    No direct reference. This is the benchmark idea behind Ch 1 and Ch 11.

    Build

    Daily simple return = percentage change in close. Equity curve = running product of (1 + return).

    Check
    • The first return is NaN. That is correct; do not fill it with a made-up value. Decide whether you drop it or start the equity curve at 1.
    • Hand identity: the final equity value must equal close[-1] / close[0]. Test it with np.isclose.

  4. Momentum baseline, without look-ahead

    Why

    The signal says "hold the stock if the past 12 months were positive". The critical detail is timing: you see today's close after the market shuts, so you can only act on today's signal tomorrow.

    Build
    1. Momentum = return over the last 252 trading days.
    2. Signal = 1 if momentum is positive, otherwise 0.
    3. Delay the signal by one day with .shift(1). Replace the resulting NaN with 0 (no position yet).
    4. Strategy return = delayed signal × that day's return.
    Check: the truncation test

    Compute the signal on the full data. Compute it again on the data cut at some date T (say, row 1000). Assert the two signals agree on every date up to T. Then separately change the close on day T+1 to a wild value and confirm the signal for day T+1 does not change (it can only depend on closes up to day T).

    Trap

    Forgetting .shift(1). The backtest will look amazing and be impossible to trade. Remove the shift on purpose once and see how big the fake improvement is; that gap is the size of the lie you are guarding against.

  5. Add transaction costs now

    Book

    Ch 11, §11.5 "A Few General Recommendations": skim for the general warnings about unrealistic backtests title checked. Execution costs are treated in Ch 14, §14.6 "Implementation Shortfall" from memory; read that later, it is not needed now.

    Why

    A strategy that trades often can look profitable before costs and lose after them. Build costs in from the start, not as an afterthought.

    Build

    A function strategy_returns(pos, ret, cost_bps) that returns pos * ret minus cost_bps / 10000 times the absolute change in position each day. A position that goes from 0 to 1 pays the cost once; from 1 to -1 pays for a change of 2.

    Check
    • With cost_bps=0 you get the gross return.
    • A position that is 0, 1, 1, 0 with 10 bps costs loses exactly 2 × 0.001 in total versus gross (one entry, one exit).

  6. Write the Sharpe ratio function

    Book

    Ch 14, §14.7.1 "The Sharpe Ratio" from memory. Read it now if you do not know what Sharpe means; you need it fluent for Phase 7.

    Build

    Sharpe = mean return divided by standard deviation of return. Two flavours, and you need both:

    • Per-period: mean / std on the daily series. PSR and DSR in Phase 7 require this one.
    • Annualised: per-period × √252. This is the number people quote.

    Write sharpe(r, periods=252) returning the annualised value, and make it easy to get the per-period one (for example periods=1).

    Check
    • On a long iid random series (rng.normal(0, 0.01, 100000)) Sharpe is near 0.
    • Multiplying every return by 3 leaves Sharpe unchanged.
    • Annualised = per-period × √252, to many decimal places.

    Trap

    Mixing annualised and per-period Sharpe in one formula is the most common error in the later statistics. Name your variables sr_pp and sr_ann and never use a bare sr.

  7. Start the trials log now

    Book

    Ch 11, §11.5 and §11.6 "Strategy Selection" title checked; the maths comes in Ch 14, §14.7.3 (DSR) from memory. You do not need to read them yet. You only need to know why you are logging.

    Why

    Try 50 settings and keep the best, and that best result is partly luck. The Deflated Sharpe Ratio in Phase 7 corrects for it, but only if it knows how many things you tried and how much their results varied. Logging afterwards from memory is unreliable.

    Build

    A log_trial(description, params, daily_returns) function in src/trials.py that:

    1. appends a row to trials.csv with columns trial_id, date, description, params, n_obs, sharpe_pp, sharpe_ann (trial_id is the previous max plus 1);
    2. saves the daily return series into data/processed/trial_returns.csv, one column per trial (named t1, t2, ...). Phase 7 needs those series for PBO;
    3. returns the new trial_id.

    Log both baselines now.

    Stuck? Hint ladder
    1. If the file does not exist yet, start from an empty DataFrame. Otherwise pd.read_csv it.
    2. For the return series: read the existing file with index_col=0, parse_dates=True, assign saved[f"t{trial_id}"] = daily_returns (pandas aligns on dates), write back.
    3. Pass the file paths as parameters with defaults, so your test can write to a temporary folder.
    Check
    • Call it twice in a test using tmp_path. trials.csv has 2 rows with ids 1 and 2, and the returns file has 2 columns.
    • sharpe_ann == sharpe_pp * sqrt(252) on every row.

Checkpoint

  • All four bad-data files raise ValueError.
  • Buy-and-hold final equity equals close[-1]/close[0].
  • The momentum signal passes the truncation test.
  • On fake data both baselines have Sharpe within about ±0.7 of zero (fake data has no edge; a 10-year single-stock Sharpe wanders that much by luck alone).
  • trials.csv has your two baseline rows.

The idea

The naive label is "did the price go up or down over the next N days?". That ignores whether the move was big enough to matter, and ignores the path (you would have been stopped out long before). AFML instead:

  • Samples events, not days. The CUSUM filter only fires when cumulative movement drifts past a threshold. Quiet days produce nothing.
  • Labels with three barriers. From each event, set a profit-taking barrier above, a stop-loss barrier below, and a time limit. The first one touched decides the label.
  • Separates direction from sizing. A simple rule picks the side (long or short). A second model predicts whether that side will be right. This is meta-labeling.

Vocabulary you will need: t0 is when the event starts. t1 is when its label is resolved (a barrier is touched). The span [t0, t1] is what makes labels overlap, which causes everything in Phases 2 and 4.

  1. Daily volatility

    Book

    Ch 3, §3.3 "Computing Dynamic Thresholds", Snippet 3.1 (getDailyVol) from memory. The book uses an exponentially weighted standard deviation with a span of 100.

    Why

    Barrier widths should scale with how volatile the stock is right now. A 2 percent move means little in a wild period and a lot in a calm one.

    Build

    daily_vol(close, span=100) -> Series. Daily log returns, then an exponentially weighted standard deviation. Require the full span of history before producing a value, so early values are NaN rather than based on two data points.

    Stuck? Hint ladder
    1. Log return: np.log(close).diff().
    2. Pandas has .ewm(span=...) and then .std().
    3. The min_periods argument of .ewm controls when values start.
    Check
    • The first span values are NaN (about 100 of them).
    • Truncation test: volatility on cut-off data matches the full-data volatility on every date up to the cut.
    • On fake data the median is about 0.01. If it is near 0.03 or 0.003, check your units.

    Trap

    A NaN volatility on an event day makes every barrier comparison false, so the event silently gets a "timed out" label. The next steps must skip those events explicitly.

  2. CUSUM filter: choose your events

    Book

    Ch 2, §2.5.2.1 "The CUSUM Filter", Snippet 2.4 (getTEvents) from memory. Also revisit the paragraph in Ch 3 that shows events being passed into getEvents.

    Why

    Sampling every day gives you highly redundant, mostly uneventful rows. CUSUM keeps two running totals, one for upward drift and one for downward drift. Each total is clamped so it never goes the wrong side of zero. When a total passes the threshold h, you record an event and reset that total.

    Build

    cusum_events(close, h) -> DatetimeIndex. Use a plain loop over daily log returns (each step depends on the previous total, so this is a place where a loop is right).

    Stuck? Hint ladder
    1. State: two floats, s_pos and s_neg, both starting at 0.
    2. Each day: s_pos = max(0, s_pos + r) and s_neg = min(0, s_neg + r).
    3. If s_pos > h: record the date, set s_pos = 0. Else if s_neg < -h: record the date, set s_neg = 0.
    4. Loop over diff.items() to get both the date and the return.
    Check: hand example

    Build a close series from log returns [+0.01, +0.01, +0.01, -0.02, -0.02, -0.02] starting at price 100, with h = 0.025. Work out by hand which days fire, then assert it. (Answer: the 3rd and 5th return days. The up-total reaches 0.03 on day 3; then the down-total reaches -0.04 on day 5.)

    Choosing h

    This is your first real knob. On my fake data (daily volatility about 1 percent, 2,500 days):

    hEventsOne event every
    0.025364.7 days
    0.033108.1 days
    0.0514117.7 days

    A good start is roughly 2 to 3 times the typical daily volatility. Log every h you try. The book also describes setting the threshold relative to current volatility instead of a fixed number; try that later as a separate trial.

  3. Triple-barrier label for one event

    Book

    Ch 3, §3.4 "The Triple-Barrier Method": Snippet 3.2 (applyPtSlOnT1), Snippet 3.4 (addVerticalBarrier) from memory. Read the figure showing the three barriers first.

    Why

    From the close at t0, set an upper barrier pt volatilities above and a lower barrier sl volatilities below, plus a limit of max_bars days. Walk forward day by day. The first barrier touched sets the label: +1 for the upper, -1 for the lower, 0 if time runs out.

    Build

    triple_barrier(close, sigma, t0, pt=1.0, sl=1.0, max_bars=5) -> (t1, label). Return both when the label resolved and what it is. Barrier levels: p0 * exp(+pt * sigma[t0]) and p0 * exp(-sl * sigma[t0]).

    Stuck? Hint ladder
    1. Position of t0: close.index.get_loc(t0). Loop positions i0+1 to min(i0+max_bars, len-1) using .iloc.
    2. Inside the loop, compare the price with the upper level first, then the lower.
    3. If the loop ends with no touch, return the last date examined and 0.
    4. If sigma[t0] is NaN, raise an error instead of returning a label.
    Check: three unit tests (write these first)

    Use a sigma of 0.01 (barriers about ±1 percent) and 4 or 5 business days:

    Closesmax_barsExpected labelExpected t1
    100, 100, 105, 903+1day 2 (third close)
    100, 100, 95, 1103-1day 2
    100, 100.1, 99.9, 100.05, 100.030day 3 (time out)

    Traps

    • Returning only the label. You need t1 in Phases 2, 4 and 7.
    • Using the window up to and including t0 to test barriers. The walk starts the day after t0.
    • This uses closing prices only. Intraday highs and lows could touch a barrier earlier; the book also works from closes, so that is fine for now.

  4. Apply it to every event

    Book

    Ch 3, Snippet 3.3 (getEvents) and Snippet 3.5 (getBins) from memory. The book returns two objects, events (with t1) and bins (with the label); you may keep them in one table.

    Build

    get_labels(close, sigma, events, pt, sl, max_bars) -> DataFrame indexed by t0 with columns t1 and label. Skip, rather than label, any event where:

    • sigma is NaN; or
    • fewer than max_bars days remain in the data (the horizon is incomplete, so a "time out" would be a fake label).
    Check

The idea

Labels overlap. Event A runs from day 1 to day 5, and event B starts on day 3. On days 3 to 5 they describe the same price moves. If you treat them as independent, the model sees the same information twice and overfits. The fix: weight each event by how much unique information it carries.

  • Concurrency c[d]: how many events are active on day d.
  • Uniqueness of an event: the average of 1 / c[d] over the days it covers. An event that overlaps nobody has uniqueness 1.
  • Sample weight: the book's return-attribution weight, below. It rewards events that capture big moves and splits the credit when events overlap.

Toy example (do this on paper first)

Three days. Event A covers days 1 to 2. Event B covers days 2 to 3.

DayActive eventsConcurrency c1 / c
1A11.00
2A, B20.50
3B11.00

Uniqueness of A = mean(1.00, 0.50) = 0.75. Uniqueness of B = mean(0.50, 1.00) = 0.75.

    Book

    num_concurrent(t0, t1, index) -> Series. t0 and t1 are aligned Series of event start and end dates; index is the full daily calendar. Start with zeros on every day and, for each event, add 1 to every day from t0 to t1 inclusive.

    Stuck? Hint ladder

    3. Date slices with .loc[start:end] are inclusive at both ends, which is exactly what you want here.
    Check

  2. Average uniqueness per event

    Book

    Ch 4, §4.4, Snippet 4.2 (mpSampleTW) from memory.

    Build

    avg_uniqueness(t0, t1, c) -> Series indexed like t0. For each event, take 1 / c on its days and average.

  3. Sample weights from return attribution

    Book

    Ch 4, §4.6 "Return Attribution", Snippet 4.10 (mpSampleW) from memory.

    Why

    An event whose window covered a big move deserves more weight than one over a quiet stretch. When events overlap, each day's return is shared among the events active that day, so the credit is not counted twice.

    Build

    For each event: take the daily log returns on its days (t0 to t1 inclusive), divide each by that day's concurrency, and sum them. Take the absolute value. Finally, scale all weights so their mean is 1.

    In symbols, weight of event i = | Σ over its days of (rd / cd) |.

    Check: hand numbers

    Using the toy example with day returns [0.02, 0.04, -0.01]:

    • A: 0.02/1 + 0.04/2 = 0.04. B: 0.04/2 + (-0.01)/1 = 0.01.
    • Scaled so the mean is 1: A = 1.6, B = 0.4.

    Traps

    • An earlier version of this guide used uniqueness × |return|. That is a simplification; use the book's version above.
    • Use log returns, so returns add up across days.
    • A weight of zero or NaN means a window with no usable returns. Assert there are none.
    • The inclusive-window convention here follows the book. Your backtest in Phase 6 earns returns from the day after t0. The two conventions differ by one day; that is acceptable, just know it.

  4. Time decay (optional build)

    Book

    Ch 4, §4.7 "Time Decay", Snippet 4.11 (getTimeDecay) from memory.

    Why

    Older observations may matter less. The book decays weights linearly with cumulative uniqueness instead of calendar time, so a stretch with many overlapping events does not age faster than it should.

    Build (optional)

    A function taking the average-uniqueness Series and a last_weight parameter. last_weight = 1 means no decay. last_weight = 0 means the oldest weight approaches 0. Multiply it into your sample weights only if you want to test it, and log it as a trial.

    Check
    • With last_weight = 1 every factor equals 1.
    • With last_weight = 0 the factors rise from about 0 (oldest) to 1 (newest) and never go negative.

  5. Know where weights get used

    Book

    Ch 4, §4.5 (bagging and sample weights) and Ch 7, §7.5 from memory.

    Rules
    • Pass the weights to the model's fit via sample_weight, and to the scoring function as well. Otherwise training and scoring disagree about what matters.
    • Rescale to mean 1 after you subset to the rows that survive later filters (such as dropping events with NaN features). Do that once, in one place, and add an assert.
    • Weights depend only on label timing and the realised return inside each event's own window, so computing them on all events before splitting is standard.

Checkpoint

  • The toy concurrency [1, 2, 1], uniqueness 0.75 and 0.75, and weights 1.6 and 0.4 all match your pencil-and-paper values.
  • On your real labels: weights average 1, none are negative or NaN, and the mean uniqueness is a number you can explain from how densely your events sit.

Common mistakes

  • Forgetting that t1 is inclusive. An event that ends on day 2 covers day 2.
  • Passing t0 and t1 with different index types (one a Series with dates as values, the other with dates as index). Keep them as aligned Series whose values are dates.
  • Using simple instead of log returns in the attribution sum.

The idea

Models need stationary inputs (statistics that do not drift over time). Prices are not stationary. Returns are, but returns throw away the memory of the price level. Fractional differencing sits between the two. With a number d between 0 and 1:

  • d = 0: the series is unchanged (full memory, not stationary).
  • d = 1: ordinary return (stationary, almost no memory).
  • In between: a weighted sum of past values. You want the smallest d that passes the ADF test, because smaller d keeps more memory.

  1. Compute the weights by hand, then in code

    Book

    Ch 5, §5.4.2 for the recurrence, §5.5.1 Snippet 5.1 (getWeights) from memory.

    Why

    The weights start at 1 for the newest value and decay for older ones. Each new weight comes from the previous: w_k = -w_(k-1) × (d - k + 1) / k.

    First, on paper

    Compute weights for d = 0.4: w0 = 1, w1 = -0.4, w2 = -0.12, w3 = -0.064, w4 = -0.0416. Verify w2 yourself from the formula before reading code.

    Build

    frac_weights(d, thresh) -> ndarray. Keep adding weights until one's absolute value falls below thresh. Return them oldest first, so the last element is the weight of the newest observation (which is 1).

    Check
    • d = 0.4 reproduces the numbers above (reversed).
    • d = 1 gives [-1, 1] (reversed: the difference of two consecutive values).
    • d = 0 gives [1].

  2. Choose the weight threshold: it decides how much data you lose

    Book

    Ch 5, §5.5.2 (the thres parameter of fracDiff_FFD) and the discussion in §5.6 from memory.

    Why

    The fixed window stops where weights become tiny, and the first width - 1 output values do not exist. The book's code default is 1e-5, which suits long high-frequency series. On daily data it is a trap:

    dthresh 1e-51e-41e-31e-2
    0.32,275 days3886612
    0.41,4582825511
    0.59272004410
    0.822864186

    Window width (number of weights) from my own run. At 1e-5 and d = 0.35, about 1,800 of 2,500 days would be lost. With 10 years of data, that kills the sample.

    Decision

    Use 1e-3 for daily bars, and write down that you deviated from the book's default and why. A larger threshold means a shorter window, so less memory is actually retained. That is a real trade-off, not free. Treat the threshold as a trial.

  3. Apply the weights with a fixed-width window

    Book

    Ch 5, §5.5.2, Snippet 5.3 (fracDiff_FFD) from memory.

    Build

    frac_diff(log_price, d, thresh) -> Series. Each output value is the dot product of the weights with the last width log prices. The first width - 1 rows have no full window and stay NaN. Apply it to log prices.

    Stuck? Hint ladder
    1. Get w = frac_weights(d, thresh) and width = len(w).
    2. Convert to NumPy: values = log_price.values; make an output array of np.nan.
    3. For each position i from width - 1 to the end, take values[i - width + 1 : i + 1] and np.dot it with w.
    4. Wrap the result in a Series with the same index.
    Check: two identities
    • d = 1 must equal log_price.diff() (ordinary log return) on every row where both exist.
    • d = 0 must equal log_price itself.
    • Number of leading NaN equals width - 1.

  4. Search for the smallest d that passes ADF

    Book

    Ch 5, §5.6, Snippet 5.4 (plotMinFFD) from memory. The book runs ADF with maxlag=1, a constant, and no automatic lag selection, then compares the statistic with the 95 percent critical value.

    Why

    The ADF test's null hypothesis is a unit root, meaning non-stationary. A p-value below 0.05 rejects that, so the series is acceptably stationary. You loop over a grid of d values from small to large and stop at the first that passes.

    Build

    min_d(log_price, grid) -> (d, p_value) using statsmodels.tsa.stattools.adfuller. Matching the book: maxlag=1, regression="c", autolag=None. If nothing in the grid passes, return (None, None) and make the caller handle it. Do not return a default.

    Check
    • On fake random-walk prices, d lands somewhere between 0 and about 0.4 (I saw 0.0 to 0.4 across seeds). d = 0 usually fails on a random walk, but it can pass by luck on a given sample (it did on one of my fake series). That says ADF is a blunt test, not that prices are stationary.
    • On a pure white-noise series (already stationary), d = 0 passes immediately.
    • The function returns (None, None), not a made-up number, when nothing passes. Test the path with an empty grid.

    Traps

    • Running ADF on the raw price instead of the fractionally differentiated series.
    • Choosing d by eye. Let the search decide, then log it.
    • A single d picked from the whole history uses future information in a small way. It is one number, so the harm is limited, but the strict approach is to choose it from the earliest part of the data. Note it in your limitations.

  5. Check that memory is kept

    Book

    Ch 5, §5.6, the figure plotting ADF statistic and correlation against d from memory. Reproduce that figure for your own series.

    Build

    For a grid of d values, compute the correlation between the fracdiff series and the original log price (over rows where both exist) and the ADF statistic. Plot both against d with matplotlib.

    Check
    • Correlation with price falls as d rises. At d = 1 it is near zero.
    • At your chosen d, the correlation is clearly above that of d = 1. If it is not, you lost the memory you were trying to keep.

  6. Build the feature matrix X

    Book

    The book does not prescribe a feature set; Part 4 (Ch 17 to 19) covers specialised features, mostly structural breaks, entropy and microstructure. Skip those for now. The look-ahead rule is the same one as everywhere in Ch 2 to 7.

    Why

    A model needs inputs. Start small and plain, so that Phase 5's importance results are readable.

    Build

    • fracdiff: your fractionally differentiated log price.
    • ret_1, ret_5, ret_21: log return over 1, 5 and 21 days.
    • vol_21: rolling standard deviation of daily log returns over 21 days.
    • zscore_20: (close minus its 20-day mean) divided by its 20-day standard deviation.

    Check

    • X, y, w, t1 all have the same index: assert X.index.equals(y.index), and so on.

  • ADF p-value is below 0.05 at the chosen d; correlation with log price is still clearly positive.
  • Every column in X passes the truncation test.
  • You have the plot from step 3.5 saved to look at.

The idea

Ordinary K-Fold shuffles data and splits it into folds. In finance that leaks information in two ways:

  • Overlap: a training event can run past the start of a test event, so the model learns the answer to a test question.
  • Serial correlation: observations right next to the test window carry information about it.

Purging removes training events whose label window [t0, t1] overlaps the test window. Embargo removes a further block of training events just after the test window.

  1. Draw the problem on paper

    Do

    Draw a timeline. Mark a test fold as a shaded block. Draw ten events as horizontal bars [t0, t1], some ending inside the shaded block, some starting inside it, some entirely before and after. Colour which ones would leak. Write down the rule you would use to remove them. This is the actual algorithm; the code is a transcription.

    Check

    Your rule should say, in words: an event is unusable if its interval touches the test window, that is, t0 <= test_end and t1 >= test_start.

  2. Core function: which training events survive?

    Book

    Ch 7, §7.4.1 Snippet 7.1 and §7.4.2 Snippet 7.2 (getTrainTimes, getEmbargoTimes) from memory. Read after you have your own version.

    Build

    A function that takes the event start times, the event end times, one or more contiguous test groups (arrays of row positions), and an embargo size in events. It returns the row positions that may be used for training. Make it accept a list of test groups now. In Phase 7, CPCV has several test groups at once and you will reuse this.

    Approach
    1. Start with every row allowed.
    2. For each test group: block its own rows.
    3. Find the group's window: start = t0 of its first row, end = the largest t1 among its rows (labels reach past the last t0).
    4. Purge: block every row whose [t0, t1] touches that window.
    5. Embargo: block the next embargo rows that start after the window ends.
    Stuck? Hint ladder
    1. Use a boolean array train_mask = np.ones(n, dtype=bool) and set entries to False.
    2. Work with t0.values and t1.values (NumPy datetimes), not Series, so comparisons are plain vectorised operations.
    3. Purge mask: (t0_values <= g_end) & (t1_values >= g_start).
    4. Where do embargoed rows begin? np.searchsorted(t0_values, g_end, side="right") gives the first row starting after the window ends.
    5. Return np.flatnonzero(train_mask).

    Traps

    • Using the last row's t0 as the window end. The window must end at the largest t1, otherwise events whose labels reach into the test period slip through.
    • Starting the embargo right after the last test row instead of after the window's end time. With long labels the purge already covers that stretch and your embargo then does nothing.
    • Events must be sorted by t0 for searchsorted to work.

  3. Wrap it in a PurgedKFold class

    Book

    Ch 7, §7.4.3 Snippet 7.3 (PurgedKFold) from memory. The book subclasses scikit-learn's KFold; you do not have to.

    Build

    A class with n_splits (default 5) and embargo_pct (default 0.01, from §7.4.2). A split(X, t1) method that is a generator yielding (train_positions, test_positions). Folds are contiguous blocks (np.array_split(np.arange(n), n_splits)), never shuffled. The embargo size in events is int(n * embargo_pct).

    Check
    • The test folds together cover every row exactly once.
    • Calling split twice gives the same folds. Use list(cv.split(...)) if you need to loop twice.

  4. Write the leakage test, then try to break it

    Build the test

    Make a toy dataset inside the test (no fixtures): 500 business days, one event per day, each ending 5 days later (t1 = t0 + 5 rows, capped at the last row). For every fold assert:

    • train and test positions do not intersect;
    • no training event's [t0, t1] touches the test window: no training row with t0 <= test_end and t1 >= test_start;
    • none of the embargo rows right after the window is in the training set.

    Add a second test: with embargo_pct = 0, the number of rows removed (total minus train minus test) is greater than zero for at least one fold. Long labels must cost training rows.

    Break it on purpose

    Temporarily disable the purge line in your function. Confirm your leakage test fails. Then restore it. A test you have never seen fail is a test you do not know works.

    Trap

    If you accidentally pass the event start as t1, every window has zero length, the purge removes nothing, and your leakage test (written with the same wrong t1) still passes. That is why the toy has genuinely long labels.

  5. Use it for out-of-fold predictions

    Book

    Ch 7, §7.5 and Snippet 7.4 (cvScore) from memory. The book wraps scoring so that sample weights reach both fit and the scorer, and uses neg_log_loss rather than accuracy.

    Build

    A plain loop (clearer than scikit-learn's helpers). Use any simple classifier for now, such as scikit-learn's LogisticRegression or the LightGBM settings from Phase 5. For each fold: fit the model on the training rows with their sample weights, predict the probability of class 1 on the test rows, store it. At the end every event has exactly one out-of-fold probability, from a model that never saw it or anything overlapping it. Keep that Series; Phases 5, 6 and 7 use it.

    Check
    • The out-of-fold Series has no NaN and every value is between 0 and 1.
    • Shuffle test: replace y with a randomly shuffled copy and repeat. A coin flip scores ln 2 = 0.693 in log loss. A model fitting pure noise usually scores at or a bit above that, and AUC stays near 0.5 (give it about ±0.08 of wobble with a few hundred events). A shuffled-label log loss clearly below 0.69, or an AUC that is well above 0.55 run after run, means something leaks.

Checkpoint

  • The leakage test passes for every fold and fails when you disable the purge.
  • You can print how many training rows each fold lost to the purge. It is a noticeable number on a dataset with long labels.
  • The shuffled-label score is at chance.

Common mistakes

  • Using sklearn.model_selection.KFold or cross_val_score with default settings. They shuffle and do not purge, so your scores can be inflated. (Be honest about the evidence: I tried to show this on fake data and mostly could not, see Phase 8, step 8.4. The leak is real but its size depends on label overlap and on the features. Rely on the leakage test, not on "my score looks fine".)
  • Setting t1 to the event start instead of the label end. The purge then does nothing.
  • Fitting a scaler on all the data before splitting. Fit transformations inside each training fold.
  • Scoring with accuracy. The book (§7.5 and Ch 9) argues for log loss because accuracy ignores confidence and weights.

The idea

A model that scores well can still be using noise. Feature importance answers "which inputs does the model actually use?". Three methods, three viewpoints:

  • MDI (mean decrease impurity): read off the trees at training time. Fast, but only describes the training data and favours features with many distinct values.
  • MDA (mean decrease accuracy): shuffle one feature on held-out data and see how much the score gets worse. Out-of-sample, but correlated features can hide each other.
  • SFI (single feature importance): train on one feature at a time. No interaction or substitution effects, but it also cannot see features that only work together.

If the three disagree wildly, or the ranking flips from fold to fold, the signal is probably noise.

    Build

    Assemble X (features), y (meta-label), w (weights) and t1 (label end), all on the same event index. Write one small function that asserts they are aligned, has the same length, and that y has both classes. Call it everywhere.

    Check

    The assertion fails if you deliberately drop one row from w.

  2. Train a small baseline and score it against a constant guess

    Book

    Build

Fixed random_state, n_jobs=1, verbose=-1, and importance_type="gain". Fit with sample_weight. Write a helper that raises an error if a training fold contains only one class.

    Using your Phase 4 loop, collect the out-of-fold probabilities and compute the weighted log loss and the AUC. Compare with the constant baseline: always predicting the weighted average of y.

    Check: what to expect on fake data

    On random data the model should not beat the baseline. In my runs, out-of-fold log loss ranged from about 0.65 to 0.78 against a baseline near 0.69. Usually worse, occasionally better by luck. AUC hovered around 0.5 (0.47 to 0.57). That is the correct result when there is nothing to find, and it is your reference for how much "skill" luck can fake with a few hundred events.

    Book

    Build

    Check

    The values sum to 1. Do the noise columns get roughly equal, low shares? If a noise column ranks near the top, MDI is flattering your training fit (that is the point of the next step).

  4. MDA on held-out folds

    Book

    Ch 8, §8.3.2, Snippet 8.3 (featImpMDA) from memory.

    Build

    For each purged fold: fit on the training rows, compute the weighted log loss on the test rows, then for each feature shuffle that column in the test rows only, recompute the loss and record shuffled - base. Use a fixed random generator (np.random.default_rng(42)) so results repeat. Return a table with one row per fold and one column per feature.

    Check
    • Copy the test frame before shuffling, so you never change the real data.
    • Pass labels=[0, 1] to log_loss in case a small test fold has one class.
    • Read the result with care. A positive MDA means "this model relies on this feature". It does not mean the feature is useful. In my random-data runs ret_1 often showed a large positive MDA (up to about 0.2) while the model's own log loss was worse than the constant guess. Always look at the score from step 5.2 before trusting an importance ranking.

  5. SFI: one feature at a time

    Book

    Ch 8, §8.4.1, Snippet 8.4 (auxFeatImpSFI) from memory.

    Build

    For each column: run your purged CV with a model fitted on that single column, and average the held-out score. Use the negative log loss so that higher means better. Return a Series. Use an even smaller model here (fewer leaves) to limit overfitting on one column.

    Check

    Compare each feature's SFI score with the constant-guess score (negative of the baseline log loss). A feature is only informative alone if it beats that baseline. On random data, none will.

  6. Judge against the noise columns and across folds

    Book

    The same logic as Ch 8, §8.6, where the book injects noise features and checks that the methods rank them last from memory.

    Build
    • For each method, rank the features, and mark where noise_1 and noise_2 land.
    • Compare rankings across folds with Spearman rank correlation (scipy.stats.spearmanr). Compute it for several fold pairs, not just one.
    • Noise baseline: rerun the whole thing after shuffling y; the rank correlations you get then are what "no signal" looks like.
    Check
    • On random data fold-to-fold agreement is erratic. In six runs of mine it ranged from about -0.55 to +0.98 from one pair of folds. With a few hundred events a single fold pair tells you almost nothing, so average over many pairs.
    • A real feature should (a) beat both noise columns under MDA and SFI, (b) hold its rank across folds, and (c) come with a model that beats the constant baseline. Without all three, do not believe it.
    • Plant a leak as a test of the test: add a column equal to tomorrow's return and confirm MDA and SFI put it first and the score jumps. This proves your tools can detect a leak.

Checkpoint

  • On fake data: the model does not reliably beat the constant baseline, noise columns land mid-pack, and fold-to-fold agreement is poor. That is the right answer.
  • With a planted leak column: it ranks first under MDA and SFI, and the out-of-fold score becomes far better than baseline.
  • You can say for each importance method what it can and cannot see.

Common mistakes

  • Trusting MDI alone. It is computed on training data, so it can rank a feature highly that the model merely memorised.
  • Computing MDA or SFI on leaking (non-purged) folds, which makes importance meaningless.
  • Reading an importance ranking from a model that does not beat the constant baseline.
  • Tuning many hyper-parameters at once. Keep the model simple so importance is readable.

The idea

The classifier says how likely it is that the primary side is right. Instead of betting the same amount every time, bet more when that probability is high and less when it is near 50 percent. Then average the bets that overlap in time, round the result to a few levels so tiny probability changes do not cause trades, and charge costs on what remains.

  1. Convert a probability into a bet size

    Book

    Ch 10, §10.3, Snippet 10.1 (getSignal) title checked. The book shows the derivation and the general multi-class form; read the binary case first.

    Build

    bet_size(p) -> array. For a binary outcome: z = (p - 0.5) / sqrt(p * (1 - p)), then size = 2 * Phi(z) - 1, where Phi is the standard normal CDF (scipy.stats.norm.cdf). Clip p to [1e-6, 1 - 1e-6] first so the formula never divides by zero.

    Check: anchor values
    • bet_size(0.5) = 0.
    • bet_size(0.9) = 0.8176 and bet_size(0.1) = -0.8176.
    • All outputs lie in [-1, 1], with no NaN, for p from 0 to 1. The function rises as p rises.

  2. Combine size with the side, and decide what a low probability means

    Book

    Ch 10, §10.3 and Ch 3, §3.6 on meta-labeling title checked / from memory.

    Decision to make

    Your classifier predicts "the primary side is right". If it says p = 0.3, the formula gives a negative size, which would flip the position against the primary side. I recommend not flipping: clip the size at 0 (no trade). The meta-model was trained to separate "right" from "wrong or stopped out". It was not trained to say that the opposite trade would have won, and a stopped-out long is not the same as a profitable short. State your choice in your notes and try the flipped variant later as a separate, logged trial.

    Build

    size = side * max(0, bet_size(p)), one value per event.

    Check

    Where p < 0.5 your size is exactly 0. Every size has the same sign as side or is 0.

    Look at your probabilities before you trust them

    Print the range and a histogram of the out-of-fold probabilities. On pure noise my LightGBM model still produced probabilities from 0.06 to 0.92, so the sizing formula bet large amounts on nothing. A model that is overconfident out of sample produces big wrong bets. Fixes: a smaller model (fewer trees, bigger minimum leaf), averaging several seeds, or calibrating the probabilities using only out-of-fold predictions. A quick diagnostic is a reliability table: bucket p into deciles and compare the average p with the actual hit rate in each bucket.

  3. Average the active bets into one position per day

    Book

    Ch 10, §10.4, Snippet 10.2 (avgActiveSignals) title checked.

    Why

    Events overlap. On some days two or three bets are open at once. The book's rule: the position on each day is the average of the bet sizes active that day. No active bet means no position.

    Build

    daily_positions(t0, t1, size, calendar) -> Series with one value for every day in the calendar. A bet opened at the close of t0 is active on the days after t0 up to and including t1 (it earns the returns of those days, not the return of t0 itself).

    Stuck? Hint ladder
    1. Two NumPy arrays the length of the calendar: a running total of sizes and a count of active bets.
    2. Loop over events. Get positions with calendar.get_loc(t0) and calendar.get_loc(t1).
    3. Add the size to total[i0+1 : i1+1] and 1 to count[i0+1 : i1+1].
    4. Position = total / count where count > 0, otherwise 0. Use np.divide(..., where=...) or mask.
    Check: toy example

    Six days, indexed 0 to 5. Bet A opens at the close of day 0, closes day 3, size 1.0. Bet B opens at the close of day 1, closes day 4, size 0.5. Expected positions: [0, 1.0, 0.75, 0.75, 0.5, 0]. (Day 2 and 3 have both bets active: the average of 1.0 and 0.5.)

  4. Discretize

    Book

    Ch 10, §10.5, Snippet 10.3 (discreteSignal) title checked. The book rounds the averaged signal.

    Build

    discretize(m, step=0.1): round to the nearest multiple of step. Apply it to the daily averaged position from step 6.3 (average first, round second, the order the book uses). Fewer distinct levels means fewer trades.

    Check
    • [0.04, 0.06, 0.84] with step 0.1 gives [0.0, 0.1, 0.8].
    • Count how many times the position changes per year before and after rounding. It must go down.

  5. Daily strategy return with costs

    Build

    Reuse your Phase 0 cost function: position × that day's return minus cost_bps times the absolute daily change in position. Start with 5 basis points. Do the same for the fixed-size version (the position uses just side, size 1 for every bet, still averaged over active bets).

    Check
    • The return series has the full calendar length and no NaN (fill days with no position with 0).
    • With zero costs, total return of a constant +1 position equals buy-and-hold over the same days.
    • Increasing cost_bps never increases any Sharpe.

  6. Compare fixed against sized on identical predictions

    Build

    Using the same out-of-fold probabilities, produce both return series. Report for each: annualised Sharpe, total turnover (sum of absolute position changes), and the Sharpe lost to costs (gross minus net). Log both with log_trial.

    Check

    • On fake data neither should show a reliable edge. Over 16 seeds, after 5 bps costs, my fixed-size Sharpe averaged -0.12 (standard deviation 0.29) and the probability-sized one averaged -0.15 (standard deviation 0.39). A gap of a few tenths between the two on a single series is noise.

Checkpoint

  • Anchor values of bet_size, discretization and the toy position example all match.
  • Bet sizes stay within -1 and 1 with no NaN; probabilities near 0.5 give sizes near 0.
  • Fixed and sized return series are saved in trials.csv and the returns file.

Common mistakes

  • Training and evaluating the classifier on the same data. Use out-of-fold probabilities only.
  • Judging only the gross return. A sizing method that trades constantly can lose to costs even with a better gross return. Always look at turnover.
  • Starting a bet's return on day t0 instead of the day after. That quietly gives you one day of returns you could not have earned.

The idea

One backtest gives one Sharpe ratio, and that number is almost always too optimistic. Three separate problems:

  • Single path: one historical path is one sample of what could have happened. Combinatorial purged cross-validation (CPCV) builds many out-of-sample paths from the same data, giving a distribution of Sharpe ratios.
  • Luck and shape: the Probabilistic Sharpe Ratio (PSR) is the probability that the true Sharpe is above a benchmark, given the sample length and the skew and fat tails of returns.
  • Selection: if you tried many configurations and kept the best, its Sharpe is inflated. The Deflated Sharpe Ratio (DSR) raises the benchmark to the Sharpe you would expect from the best of N pure-luck trials.

The Probability of Backtest Overfitting (PBO) estimates how often the configuration that was best in-sample ranks below the median out-of-sample.

  1. Make sure the raw material is there

    Check before starting
    • trials.csv holds every configuration you tried, with sharpe_pp per row, and data/processed/trial_returns.csv holds each trial's daily return series.
    • You can produce out-of-fold daily returns for one configuration from raw prices in a single function call. Chain Phases 1 to 6 into one function, run_config(prices, **settings), returning the daily return series. You need to call it many times with different settings.

  2. Work out CPCV by hand

    Book

    Ch 12, §12.4.1 "Combinatorial Splits" and §12.4.3 "A Few Examples" title checked. The book has a figure with a grid of groups and splits.

    Idea

    Split the timeline (your events, in order) into N contiguous groups. Every choice of k groups becomes the test set once, and the rest is training (with purging and embargo at every boundary). That gives C(N, k) splits. Each group is a test group in C(N-1, k-1) of them. Stitching one out-of-sample prediction per group gives a complete path, and you can build k × C(N, k) / N distinct paths.

    Do on paper

    Take N = 4, k = 2. List the 6 splits. Check that each of the 4 groups is out of sample 3 times. Check that you can build 3 paths. Then confirm the formula for N = 6, k = 2: 15 splits and 5 paths.

    Check

    Write a tiny function that returns the path count and test it against 3 and 5.

  3. Train and predict on every split

    Book

    Ch 12, §12.4.2 "The Combinatorial Purged Cross-Validation Backtesting Algorithm" title checked.

    Build

    Loop over all combinations of test groups (itertools.combinations). For each: compute the training rows using your Phase 4 function with several test groups at once (it purges and embargoes around each group, which is why you made it accept a list). Fit a fresh model on those rows and predict the probability for the rows of each test group. Store the predictions by (group, order of appearance).

    Check
    • The number of fitted models equals C(N, k).
    • Extend your leakage test: for every split, no training row touches the window of any test group, including the groups that are not adjacent to each other.
    • Each group appears as a test group exactly C(N-1, k-1) times.

  4. Stitch paths and compute a Sharpe for each

    Build

    Path number j takes, for every group g, the prediction from the j-th split in which g was out of sample. Each path then has exactly one out-of-sample probability for every event. For each path: size the bets (Phase 6, including averaging, discretizing and costs) to a daily return series and compute its Sharpe.

    Check
    • Every path has the full set of events, each exactly once.
    • Report the median, the 5th percentile, and the spread of your path Sharpe ratios, not the best one.
    • Calibrate against luck. On zero-drift fake data (2,500 days, 5 bps costs) the median-path Sharpe across 16 random seeds averaged -0.15 with a standard deviation of 0.39, ranging from -0.84 to +0.41. So a result within about ±0.8 on a single stock is consistent with no skill at all.
    • Paths share training data and are strongly correlated with each other. Five paths are not five independent experiments.

  5. Probabilistic Sharpe Ratio (PSR)

    Book

    Ch 14, §14.7.2 from memory. Original: Bailey and López de Prado, "The Sharpe Ratio Efficient Frontier" (Journal of Risk, 2012).

    Idea

    PSR is the probability that the true Sharpe exceeds a benchmark SR*, given the estimated Sharpe SR, the number of observations n, and the skewness g3 and kurtosis g4 of the returns:

    PSR = Phi( (SR - SR*) × sqrt(n - 1) / sqrt(1 - g3 × SR + (g4 - 1)/4 × SR²) )

    Build

    psr(returns, sr_star=0.0). All Sharpe values here are per-period (daily), not annualised. Use scipy.stats.skew and scipy.stats.kurtosis(..., fisher=False). The default of kurtosis returns excess kurtosis (normal = 0). The formula needs raw kurtosis (normal = 3). The wrong default silently gives wrong answers.

    Check
    • psr(r, sr_star=SR_of_r) returns exactly 0.5.
    • More observations (same Sharpe) increases PSR when SR > SR*.
    • On fake data, PSR against 0 is often well above 0.5 for a lucky series. That is the point of the next step.

  6. Deflated Sharpe Ratio (DSR)

    Book

    Ch 14, §14.7.3 from memory. Original: Bailey and López de Prado, "The Deflated Sharpe Ratio" (Journal of Portfolio Management, 2014). Ch 11, §11.6 explains why this is needed.

    Idea

    DSR is PSR where the benchmark SR* is the Sharpe you would expect from the best of N trials with no skill. With V the variance of Sharpe estimates across your trials and gamma the Euler-Mascheroni constant (about 0.5772):

    SR* = sqrt(V) × [ (1 - gamma) × Phi^-1(1 - 1/N) + gamma × Phi^-1(1 - 1/(N×e)) ]

    Build
    1. expected_max_sr(sr_var, n_trials) implementing the bracket above (norm.ppf is Phi^-1). Raise an error if n_trials < 2.
    2. dsr(returns, trial_sharpes_pp): take N as the number of trials and V as the variance of the per-period Sharpe column in trials.csv, then return psr(returns, sr_star).
    Check
    • expected_max_sr grows as N grows, and as V grows.
    • DSR is lower than PSR whenever SR* > 0.

    Traps

    • Leaving out failed or abandoned experiments from trials.csv. This is the most common way DSR is wrong in practice.
    • Mixing annualised and per-period Sharpe. V and the strategy Sharpe must be in the same units.
    • N = number of rows overstates the number of independent trials when your configurations are highly correlated; the book discusses estimating the effective number (look in Ch 14 and Ch 11). Treat N = len(trials) as a simple first version and say so.

  7. Probability of Backtest Overfitting (PBO)

    Book

    Discussed in Ch 11 and Ch 12 (§12.5) from memory. Procedure: the paper by Bailey, Borwein, López de Prado and Zhu named in the reading plan.

    Idea (CSCV, combinatorially symmetric cross-validation)

    You have a table of daily returns: one column per configuration you tried, same dates. Ask: "if I pick the configuration that looked best on half the data, how does it do on the other half?"

    1. Cut the rows into an even number S (for example 10) of equal time blocks.
    2. For each way of choosing S/2 blocks as in-sample (the rest is out-of-sample):
      • compute every configuration's Sharpe in-sample and pick the best one;
      • compute every configuration's Sharpe out-of-sample, and find where the chosen one ranks;
      • turn that rank into a relative rank w = rank / (number of configs + 1) and take the logit ln(w / (1 - w)).
    3. PBO = the fraction of splits where the logit is at or below 0, meaning the chosen configuration landed at or below the median out of sample.
    Build

    pbo(returns_table, n_blocks=10). With 10 blocks that is 252 splits, which is quick.

    Check
    • Independent random columns (for example 30 columns of rng.normal(0, 0.01, 1000)): PBO comes out near 0.5 on average, but a single run wanders a lot. Over 10 seeds I got values between 0.29 and 0.70, mean 0.48.
    • One genuinely better column (add 0.002 to every row of one column): PBO drops close to 0 (I got 0.02).
    • Real configurations of one strategy are not independent, and PBO behaves differently. On my nine correlated null configurations (different h and barrier widths on the same fake series) it came out at about 0.79, well above 0.5. My explanation, not proven: configurations that share most of their positions also share most of their luck, and because the in-sample and out-of-sample halves are complements of the same sample, "best in-sample" tends to mean "luckiest in this half" and then pays it back in the other half. So treat PBO as a warning light that gets more reliable with more, and more varied, trials. A high value means selecting among your trials is not trustworthy.

    Build

Write a paragraph in your own words saying whether you believe the result and why.

  • Path counts match the formula (3 for N=4,k=2; 5 for N=6,k=2) and the multi-group leakage test passes.
  • You report a distribution of path Sharpe ratios, never just the best one.
  • PSR(sr_star = own Sharpe) equals 0.5; DSR is below PSR; PBO passes both random-column checks.
  • All Sharpe values entering PSR and DSR are per-period.

Common mistakes

  • Reporting the best path's Sharpe. Report the distribution.
  • Leaving failed experiments out of trials.csv.
  • Mixing annualised and per-period Sharpe values.
  • Using kurtosis with its default (excess) setting inside PSR.
  • Treating the CPCV paths as independent evidence. They are not.

  • Why does the number of trials push the benchmark Sharpe up?
  • In what way is a high PSR still compatible with having no skill?

Phase 8: Capstone tests (do these before you believe anything)

Build: a test script that runs the whole pipeline on fake data  ·  Done when: the pipeline finds nothing in noise, loudly detects a planted leak, and you know how small an effect it can see.

The idea

You have built a measuring instrument. Before measuring something real, check it on cases where you already know the answer: nothing there, a leak, and a weak real effect. Do all of these before you load real data, and re-run them whenever you change the pipeline.

  1. Negative control: pure noise, many seeds

    Do

    Run the full pipeline (Phases 1 to 7) on make_prices(2500, seed=s) for at least 10 seeds with zero drift. Collect the median-path Sharpe for each.

    Expect

    A cloud centred near zero or slightly negative (costs), with a spread of roughly 0.4. Mine: mean -0.15, standard deviation 0.39, range -0.84 to +0.41 over 16 seeds. DSR should rarely be near 1.

    If you see

    A mean that is clearly positive, or many seeds above 1.0, you have a leak. Go back through the truncation tests and the leakage test.

  2. Leak control: plant a leak on purpose

    Do

    Add a feature column equal to tomorrow's return (or the sign of the label). Run the pipeline.

    Expect

    A big jump: out-of-fold AUC far above 0.5, a very high Sharpe, and the planted column ranked first by MDA and SFI. When this happened to me by accident (a noise column that shared its random seed with the price generator and so equalled the next day's return), the pipeline reported AUC 0.73 and a Sharpe of 1.7 on random data, and importance flagged the culprit immediately.

    Why it matters

    It proves that your evaluation can see a leak. Remove the planted leak afterwards.

  3. Power check: how small an effect can you see?

    Do

    Skip the price side: keep your real feature matrix and event timing, but replace y by a synthetic label that depends weakly on one feature, for example the chance of y = 1 rising from 35 percent to 65 percent as zscore_20 goes from its low to its high end. Run Phases 4 and 5 and look at the out-of-fold AUC and the importance ranking.

    Expect (and what I saw)

    With about 420 events I got out-of-fold AUCs between 0.44 and 0.56 in six seeds, and the planted feature often did not come out first. With a few hundred events, a real but modest effect is frequently invisible. This is the single most important number to carry into the real-data work: it tells you how much to trust a "nothing found" result as well as a "something found" one.

    A positive control that did not work

    I also tried planting a daily mean-reversion effect in the prices themselves. The pipeline did not profit from it (Sharpe went from about -0.10 to -0.33), because that effect lives on a 1-day horizon while the primary rule is 12-month momentum and the labels span 5 days. A positive control has to match what the strategy is designed to exploit.

  4. Mechanism control: the leakage test again

    Re-run the Phase 4 leakage test, including its "break it on purpose" check, plus the multi-group version from Phase 7. I tried to show the damage of ordinary shuffled K-Fold on fake data and mostly could not: the average AUC was 0.50 for shuffled folds and 0.50 for purged folds with a random forest, and 0.51 versus 0.50 with LightGBM. The leakage is real, but its effect on a score depends on heavy label overlap together with features that identify neighbouring events. That is why you test the mechanism directly, instead of relying on "my score looks fine".

  5. Only then: real data

    Run the pipeline on real data. Log every configuration. Report the distribution, PSR, DSR and PBO, the number of events, and the power caveat from step 8.3 in the same place as the headline number.

Checkpoint

  • Negative control: no systematic edge across seeds.
  • Leak control: loud detection.
  • You have written down, in your own words, the smallest effect you think this setup could detect.

Mistakes that ruin everything

These cause the most damage and are the hardest to notice. Check each one before you trust a result.

MistakeWhat it looks likeHow to prevent it
Look-ahead biasResults look too good, especially early in the sample.Shift signals before trading. Run the truncation test on every feature, signal and volatility estimate.
Overlapping labels leakingCross-validation scores above what the model achieves live.PurgedKFold with t1 and an embargo (Phase 4). Keep the leakage test, and its break-it-on-purpose check.
Survivorship biasBacktest only holds companies that survived to today.Include delisted tickers and point-in-time index membership. Write the limitation down if you cannot.
Selection biasYou kept the best of many configurations.Log every trial in trials.csv; report DSR and PBO.
Silent fallbacksA function returns a default when it fails, and you never notice.Raise an error or return None explicitly and handle it.
NaN poisoningA NaN side, volatility or feature makes a comparison False and silently becomes a wrong label.Drop or raise on NaN at the point of creation, and assert none remain before modelling.
Ignoring costsStrategy looks profitable but trades heavily.Charge cost per unit of turnover in every return series.
Overconfident probabilitiesSizing makes large bets on a model with no skill.Inspect the probability histogram and reliability table; regularise or calibrate out-of-fold.
Reading importance of a useless modelA feature has high MDA although the model loses to a constant guess.Always compare the out-of-fold score to the constant baseline first.
Wrong Sharpe unitsPSR or DSR gives absurd values.Use per-period Sharpe in those formulas; name variables sr_pp and sr_ann.
Trusting small samplesA single stock gives a few hundred events and an impressive Sharpe.Run the capstone controls; treat anything under about ±0.8 as consistent with luck.
